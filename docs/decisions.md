# Decisions

This is the project's decision record. Read the relevant entries before changing an area. Add short, dated entries here rather than creating separate ADR files. If a request conflicts with an accepted decision, surface the conflict before making a wider change.

The first five entries preserve the former ADRs. Their date is when those records first appeared in Git, not an inferred adoption date. They were consolidated here on October 30, 2026. The revisit conditions below identify when to reconsider them; the original records did not specify those conditions.

## Platform: Cloudflare Workers and D1
2026-10-03 · accepted

The service runs on Cloudflare Workers with D1 rather than a VPS or container-hosted reader such as FreshRSS or Miniflux. This keeps the runtime, database, scheduled work, and static assets on the existing Cloudflare platform, avoiding a separate server to operate. The trade-off is designing around Workers and D1 execution limits.

Revisit when: Workers or D1 limits prevent meeting the application's requirements.
Refs: [Worker configuration](../wrangler.jsonc), [architecture](architecture.md)

## Protocol: Google Reader through FreshRSS-compatible sync
2026-10-03 · accepted

The backend exposes the Google Reader API dialect used by FreshRSS clients, rather than implementing a reader-specific API. Current accepts a custom server URL in its FreshRSS sync mode, making this protocol the practical integration seam without requiring a FreshRSS installation. Other clients can connect when they support compatible sync.

Revisit when: required reader clients no longer support this protocol or need capabilities it cannot represent.
Refs: [GReader API](reference/greader-api.md)

## Authentication: Access for management and API Tokens for readers
2026-10-03 · accepted

Cloudflare Access protects the browser-based management interface, while named API Tokens authenticate Google Reader ClientLogin requests. Reader clients cannot complete a browser redirect flow, so they use revocable bearer tokens generated by an Access-authenticated User. Only token hashes are stored.

Revisit when: management identity or reader authentication requirements change.
Refs: [Authentication reference](auth-flow.md)

## Data ownership: shared Feeds and Items with per-User state
2026-10-03 · accepted

A Feed URL has one canonical Feed record and one shared copy of each Item, while Subscriptions and Item State are per-User. This avoids fetching and storing duplicate content for every subscriber, at the cost of carefully scoping reading state and visibility to each User's Subscriptions.

Revisit when: Feed content or polling policy must differ by User.
Refs: [Domain vocabulary](../CONTEXT.md), [schema](../src/db/schema.ts)

## Persistence: D1 is authoritative and Analytics Engine is optional
2026-10-03 · accepted

D1 is authoritative for polling outcomes, Feed health, Items, and dashboard history; Workers Analytics Engine supplies optional aggregate trends. Analytics delivery or query failures must not affect durable application behavior, and the dashboard's core activity remains available without Analytics Engine credentials.

Revisit when: the authoritative store or required analytics availability changes.
Refs: [Architecture](architecture.md), [Analytics reader](../src/feed/analytics.ts)
